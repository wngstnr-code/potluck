# S6: Public RPC throughput (Polkadot Asset Hub)

- **Run:**
  - `pnpm --filter @potluck/spikes s6` (all endpoints, levels 1–32)
  - `S6_ONLY=parity S6_LEVELS=32,64,128,192 S6_BLOCKS_PER_LEVEL=600 S6_BATCH_HASHES=1 S6_OUT=s6-rpc-throughput-parity-high pnpm --filter @potluck/spikes s6`
- **Raw output:** [`s6-rpc-throughput.json`](./s6-rpc-throughput.json), [`s6-rpc-throughput-parity-high.json`](./s6-rpc-throughput-parity-high.json)
- **Measured:** 2026-10-20, from the developer's machine (Indonesia). Latency-bound: ~450 ms per block round trip.
- **Hot loop measured:** `chain_getBlockHash` + `state_getStorage(System.Events)` per block, raw `WsProvider`.

## Implications
- `chain_getBlockHash` accepts a list of block numbers. **Batch hash lookups** and keep only one `state_getStorage` per block in flight.
- **Publisher build time** for the Polkadot AH Revive window (10,646,347 blocks at measurement), at ~250 blocks/s: **≈ 11.8 h** on one endpoint. It must be resumable (checkpoint per chunk) because sustained multi-hour behaviour was not measured here (bursts only).
- **Naive browser sync** of the same window is realistically **2–4 days** (33–63 blocks/s at 16–32 in flight, no batching), and ~56 days sequentially. The earlier "~15 h" figure in the docs assumed 200 blocks/s on one connection and is **wrong**; docs updated accordingly.
- Only one public endpoint is reliable. The publisher should support multiple endpoints but must not rely on them. Consumers verify against whichever endpoint the user configures.
