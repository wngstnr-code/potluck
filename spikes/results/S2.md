# S2: TransactionStorage fees and blob size limits (fee part; real stores need tPOT)

- **Run:** `pnpm --filter @potluck/spikes s2`
- **Raw output:** [`s2-store-fees.json`](./s2-store-fees.json)
- **Measured:** 2026-10-20 via `paymentInfo` on `wss://test-node-v3.portaldot.dev` (fee estimation needs an address, not funds)

## Findings
| Blob size | Fee |
|---|---|
| 1 KB | 0.111 tPOT |
| 100 KB | 10.01 tPOT |
| 1 MB | 100.01 tPOT |
| 4 MB | 400.01 tPOT |
| 7.8 MB | 780.01 tPOT |

- **Storing data costs ≈ 0.0001 tPOT per byte = ~100 tPOT per MB.** It is the transaction length fee, not the pallet's `byteFee` (10 planck/byte), that dominates. The earlier "8 MB ≈ 0.00000084 POT" estimate in the docs was wrong.
- **Blobs up to 7.8 MB are accepted over the public WSS endpoint.** The payload travels as hex (2× size), taking ~28 s for 7.8 MB from the developer's link, so the client needs a request timeout ≥ 90 s. The 60 s default timed out, and so does the endpoint's 60 s connection drop.
- `TransactionStorage.Stored` carries `(index, content_hash)`, so a publisher can check that the stored digest equals the manifest's `blob.digest`.

## Cost model (testnet prices, ~100 tPOT/MB)
| Item | Size | Fee |
|---|---|---|
| Polkadot AH balance history, newest 3,000 blocks (measured build) | 38.5 KB | ≈ 4 tPOT |
| Polkadot AH, newest ~1.5 M blocks (first backfill target, extrapolated) | ≈ 19 MB | ≈ 1,900 tPOT |
| Registry deploy deposits (S8) | n/a | ≈ 433 (EVM) + 3,293 (PVM) tPOT |

## Implications
- **Request ≈ 6,000–8,000 tPOT** for the MVP (both registry deployments + the first backfill + specs/manifests), or deploy EVM only and shrink the first backfill.
- Bytes are the cost driver, so encoding efficiency (per-chunk account dictionary / columnar layout) directly cuts publishing cost. This moves it up the P1 list.
- Keep chunk blobs well below the cap (≤ ~4.5 MB with `maxRawBytes` 32 MB and gzip ~7×), so each upload finishes long before the endpoint's 60 s connection drop.
