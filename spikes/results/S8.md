# S8: PotluckRegistry on Portaldot pallet-revive (EVM + PVM). Partial, dry-run only

- **Run:**
  - `pnpm --filter @potluck/contracts build:evm && pnpm --filter @potluck/contracts build:pvm`
  - `pnpm --filter @potluck/contracts dry-run`
- **Raw output:** [`s8-registry-dry-run.json`](./s8-registry-dry-run.json)
- **Measured:** 2026-10-20 against `wss://test-node-v3.portaldot.dev` (portaldot-v3 spec 3002)
- **Method:** runtime API `ReviveApi.instantiate`. It executes the constructor against live state with a funded account as origin; no signature, no funds and no tx are needed. A real deployment still needs tPOT.

## Findings
| | EVM (solc 0.8.28, Foundry, `cancun`) | PVM (resolc 1.4.0, LLVM 22, `-Oz`) |
|---|---|---|
| Code size | 5,414 bytes | 42,055 bytes (`PVM\0` magic) |
| Dry-run result | ✅ instantiated, no revert | ✅ instantiated, no revert |
| `weightRequired.refTime` | 2,552,464 | 9,014,130 |
| **Storage deposit to deploy** | **≈ 433.2 tPOT** | **≈ 3,293.4 tPOT** |

- **The same Solidity source runs on both Revive backends with an identical ABI.** This proves the dual-deployment decision (`ARCHITECTURE.md` §15 decision 2) on the real runtime.
- `cancun` EVM bytecode (PUSH0, MCOPY, etc.) is accepted by Portaldot's Revive.
- EVM code cannot be instantiated from an existing code hash (`revive.EvmConstructedFromHash`); EVM must always be uploaded. PVM code can be instantiated from a hash (verified with another team's PVM code).

## Pitfall found (applies to all Substrate-side code in core/cli)
**`@polkadot/api` treats a raw `Uint8Array` passed for a `Bytes` argument as already SCALE-encoded (compact length prefix).** Passing the contract code as a `Uint8Array` silently truncated it and produced a misleading `revive.StackUnderflow` on both VMs. **Always pass raw byte payloads (contract code, TransactionStorage blobs) as hex strings.**

## Cost implications (to confirm after the real deployment)
- Deposits are refundable when the code/storage is removed, but they must be available up front. `depositPerByte` = 0.06 tPOT, `depositPerItem` = 0.15 tPOT.
- **Request enough tPOT:** ≈ 3,800 tPOT covers both deployments, plus budget for manifests.
- **Rough per-manifest estimate** *(assumption, ~16 storage items and ~1 KB)*: tens of tPOT. If the faucet amount is small, consider a leaner layout: store only the manifest digest + range + publisher in storage and emit the rest in events, which clients read via `eth_getLogs`.
