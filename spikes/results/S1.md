# S1: Decoding events across runtime upgrades (Polkadot Asset Hub)

- **Run:** `pnpm --filter @potluck/spikes s1`
- **Raw output:** [`s1-runtime-decoding.json`](./s1-runtime-decoding.json)
- **Measured:** 2026-10-20
- **Window:** Revive activation **#11,405,259** → head.

## Findings
1. **10 runtime versions / 9 upgrades inside the window:** 2000005 → 2000006 → 2000007 → 2001001 → 2002001 → 2003000 → 2003001 → 2003002 → 2004000 → 2005000.
   - Upgrade blocks: #11,896,182, #12,319,017, #13,733,620, #14,857,499, #16,946,479, #17,297,796, #18,731,801, #20,135,078, #20,485,672.
   - The boundaries were found with 161 samples + 144 binary-search probes.
2. **Critical rule: decode a block's events with the metadata of the runtime that *executed* the block, i.e. the runtime in the *parent* state.**
   - `state_getRuntimeVersion(blockHash)` reads `:code` from the block's **post-state**. In the block that applies the upgrade (it contains `system.CodeUpdated` / `parachainSystem.ValidationFunctionApplied`), the post-state already reports the new version, while the events were produced by the old runtime.
   - **Executing-runtime rule:** 27/27 blocks around all 9 boundaries decode completely (no leftover bytes).
   - **Post-state rule:** **fails** at #16,946,479 (34 events, decode error at record 3).
3. **Metadata cost:** 561–639 KB per version (~0.6–1.1 s to fetch), **~5.8 MB for all 10 versions** in the window. Metadata is v14+ throughout (self-describing; no hand-written types).
4. **Huge blocks exist:** #20,485,673 (first block of spec 2005000, multi-block migrations) holds **1,888 events / 112,929 bytes** in one block. Chunking must split by bytes, not only by block count, and must allow a single block to exceed the "typical" size.
5. **Negative control:** the first window block decodes identically with its own and with the newest metadata, so many upgrades are event-compatible. That does **not** make per-version metadata optional, as finding 2 shows.

## Decisions / implications
- `core` resolves the decoding runtime as `runtimeVersion(parentHash)`, cached per spec version, with the runtime-version map built once per source (binary search, as here).
- Metadata blobs are large but few. The publisher can store each version's metadata in TransactionStorage next to the chunks, and the manifest can reference it. Then a browser verifier never needs a second source for metadata. (Candidate P1 feature; recorded in ARCHITECTURE.)
- The chunker enforces `maxBytes` and treats a single oversized block as its own chunk.
